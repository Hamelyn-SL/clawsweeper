- `merge-risk: 🚨 security-boundary`: The added guard relies on a request-body user value, so green CI would not prove that unauthenticated checkout requests cannot bypass registered-user coupon eligibility.

## Summary

Keep open: the patch targets the right checkout revalidation gap, but the new guard trusts the client-supplied checkout `user` field, so a direct guest request can still bypass the registered-user coupon restriction by sending any non-empty user value; the PR also lacks real behavior proof.

## What This Changes

The PR adds an `applyOnlyToRegistedUser` check to checkout promotion-code validation and records the coupon-validation lesson in issue-triage memory.

## Best Possible Solution

Final checkout validation should base registered-user coupon eligibility on the server-resolved or authenticated user, mirror the admin pre-validation contract, and include redacted live checkout/API proof for the guest rejection path.

## Reproduction Assessment

Yes from source inspection: the checkout POST handler accepts a JSON body, the caller passes `checkoutNewOrder.user` into the new guard, and guests can provide an inline address. I did not run a live checkout request in this read-only review.

## Solution Assessment

No: the guard is in the right validation phase, but it checks a client-supplied `userId` instead of the resolved server user. The narrow fix is to pass the resolved user or `user?._id` into coupon validation and reject when no resolved user exists.
