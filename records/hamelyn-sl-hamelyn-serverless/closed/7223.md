- `impact:crash-loop`: La issue trata un timeout 504 recurrente de un cron serverless, una forma concreta de fallo de disponibilidad del proceso.

## Summary

La issue sigue abierta con razón: en `dev` la ruta del cron aún hereda `maxDuration: 300`, el diagnóstico operativo confirma 504 diarios a ese límite, y el PR de cierre https://github.com/Hamelyn-SL/hamelyn-serverless/pull/7233 sigue abierto aunque esté aprobado y mergeable.

## What This Changes

La issue pide que el cron `sync-cainiao-pudo-points` deje de agotar el límite de 300 s y complete la sincronización diaria de puntos PUDO.

## Best Possible Solution

Aterrizar el PR enlazado si la revisión lo mantiene aprobado, desplegar `crons` y validar una ejecución real de Vercel con log final; después tratar el timeout de `axios` como endurecimiento separado si no entra en el mismo PR.

## Reproduction Assessment

Sí, a nivel de fuente y con evidencia operativa: el checkout actual deja la ruta bajo `maxDuration: 300`, y el comentario de triage confirma 6/6 ejecuciones programadas con 504 a unos 300 s sin log final. No ejecuté el cron contra producción desde esta revisión read-only.

## Solution Assessment

Sí para la causa inmediata: una entrada `functions` propia con más duración es la corrección más estrecha del 504 observado. Añadir `timeout` al cliente Cainiao sigue siendo una defensa útil, pero esta issue debe esperar al merge y validación del PR abierto.
