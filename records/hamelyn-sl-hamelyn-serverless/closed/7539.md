## Summary

Esta PR debe seguir abierta: la dirección general es útil, pero el caso principal de `binIn` permanece sin corregir, la respuesta nueva amplía la exposición de datos del proveedor y el contrato HTTP de Skypod aún necesita definición.

## What This Changes

La PR reutiliza el helper HTTP compartido en ocho manejadores de Admin y añade una traducción de errores 400 de Skypod a respuestas 422 en tres rutas Exotec, además de actualizar la skill interna.

## Best Possible Solution

Normalizar los errores Skypod en la frontera de integración antes de perder el `AxiosError`, exponer únicamente campos permitidos, diferenciar autenticación 401 de autorización 403 y documentar el contrato acordado para validaciones y conflictos.

Kind: product_direction

Question: ¿Qué contrato HTTP debe exponer Admin para los rechazos semánticos de Skypod: conservar 400, distinguir conflictos como 409 y validaciones como 400/422, o usar 422 para todos?

Rationale: La issue exige un 4xx, la discusión recomienda distinguir 400/409 y esta PR adopta 422 universal; no existe aún una política canónica para clasificar esos `ErrCode` y `ErrDetail`.

Likely owner: banosdavidhamelyn

Owner reason: Es el revisor solicitado con mayor historial directo en el flujo de bins y errores de Skypod.

Owner confidence: high

Options:

- **Distinguir validación y conflicto (recommended):** Mapear las validaciones a 400 o 422 y los conflictos operativos conocidos a 409, manteniendo transporte y 5xx como 502/500.
- **Conservar el 400 upstream:** Propagar un 400 sanitizado para todos los rechazos semánticos y evitar una taxonomía local adicional.
- **Adoptar 422 universal:** Mantener la propuesta actual y documentar que todo 400 de Skypod se convierte en 422, incluidos los conflictos.

Sí. El código permite reproducir con alta confianza que `processBin` convierte el error Skypod en 500 antes del helper y que una petición sin token acaba como `UserPrivilegesCheckError(403)`.

## Solution Assessment

No. Reutilizar `toErrorResponse` es correcto, pero la normalización Skypod debe hacerse antes de perder el error original, con un payload sanitizado y un contrato 400/409/422 acordado.
