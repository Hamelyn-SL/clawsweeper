- `P1`: El bypass está confirmado en código, pero el responsable ha rebajado la urgencia mientras se define una alternativa segura para la operativa de almacén.
- `impact:security`: El trabajo afecta autenticación, autorización por roles y el control de llamadas a APIs administrativas.

## Summary

La incidencia sigue siendo necesaria: `dev` conserva rutas v5 administrativas sin autorización directa y la política aún permite listas de roles vacías. La prueba desplegada sigue pendiente, pero no invalida el bypass demostrable en código.

## What This Changes

Corregir las rutas administrativas v4/v5 que admiten llamadas sin autenticación o sin una comprobación de rol efectiva.

## Best Possible Solution

Separar las llamadas humanas de los flujos máquina-a-máquina: aplicar roles explícitos a las rutas de usuario y exigir una autenticación de servicio limitada para los callbacks operativos legítimos.

Options:

- **Separar usuarios y servicios (recommended):** Proteger las rutas de panel con `withAdminRoute` y mover cada integración necesaria a una autenticación de servicio explícita y acotada.
- **Aplicar el proxy a todo v5:** Exigir Auth0 en todo `/api/v5`, aceptando que antes habrá que adaptar los clientes de almacén incompatibles.
- **Mantener excepciones temporales:** Conservar únicamente excepciones documentadas mientras se diseña la migración, asumiendo el riesgo de seguridad temporal.

## Solution Assessment

No todavía: aplicar una protección global sin distinguir clientes humanos de integraciones de almacén puede romper operaciones legítimas. La solución debe reutilizar el wrapper existente y una identidad de servicio limitada.
