## Summary

La incidencia sigue siendo necesaria: el error de Arnoia persiste y el flujo actual puede pasar el pedido a `TO_CANCEL` tras 168 horas sin confirmar si el proveedor llegó a expedirlo. Hace falta una decisión de comportamiento antes de proponer un cambio local.

## What This Changes

La incidencia solicita evitar errores internos repetidos al consultar el tracking de un pedido de dropshipping de Arnoia.

## Best Possible Solution

Mantener el límite para pedidos realmente sin tracking, pero tratar el código ambiguo `-4` con reconciliación operativa o una transición explícita que no marque cancelación sin comprobar Arnoia.

Options:

- **Reconciliar antes de cancelar (recommended):** Para `-4`, conservar el pedido pendiente y alertar a Operaciones hasta confirmar expedición, transportista o inexistencia en Arnoia.
- **Mantener el límite duro:** Conservar la cancelación a las 168 horas y aceptar el riesgo operativo de que un pedido expedido requiera recuperación posterior.
- **Aplicar una ventana distinta:** Definir un plazo específico para errores ambiguos y una transición visible de revisión antes de cualquier cancelación.

## Reproduction Assessment

No para la respuesta viva de Arnoia: los logs confirman el síntoma, pero falta la consulta al proveedor. Sí se puede seguir por código que el mismo error entra en la cancelación forzada tras 168 horas.

## Solution Assessment

No está claro que mantener la cancelación automática sea la mejor solución: el error `-4` no confirma el estado real del pedido. Una reconciliación previa reduce el riesgo de cancelar una expedición existente.
