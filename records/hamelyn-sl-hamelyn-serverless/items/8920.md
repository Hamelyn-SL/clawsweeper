## Summary

Gracias por el contexto: el incidente sigue siendo necesario porque `dev` todavía puede desplegar un PAT no vacío pero rechazado por GitHub, dejando detenida toda la familia `gh-dispatch`.

## What This Changes

Restaurar los disparos de Cloud Scheduler a GitHub Actions y validar preventivamente el token de dispatch durante el despliegue.

## Best Possible Solution

Restaurar primero el PAT aprobado, reaplicar Scheduler y comprobar un dispatch real; después, impedir nuevos despliegues inválidos mediante una verificación aislada que pruebe el permiso de escritura sin ejecutar lógica operativa.

Options:

- **Workflow de verificación aislado (recommended):** Añadir un workflow mínimo y sin efectos operativos, dispararlo desde el deploy y abortar antes del apply si GitHub lo rechaza.

## Reproduction Assessment

Sí, por fuente: un PAT no vacío se propaga a todos los jobs sin autenticarse contra GitHub. La confirmación final requiere observar el `404` con la credencial afectada en Scheduler o en una llamada autenticada equivalente.

## Solution Assessment

Sí para la recuperación inmediata, pero la validación preventiva necesita una prueba aislada de `Actions: write`; una consulta de lectura por sí sola no cubre el fallo descrito.
