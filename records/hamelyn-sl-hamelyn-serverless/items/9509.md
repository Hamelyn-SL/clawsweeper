## Label Justifications

- `P1`: La regresión deja tickets operativos sin datos y el cron propuesto puede alterar campos existentes de atención al cliente.
- `merge-risk: 🚨 compatibility`: El PUT de sincronización puede reemplazar valores personalizados existentes de tickets ya abiertos.

## Summary

El PR aborda una regresión real, pero el cron puede borrar valores válidos, conservar datos calculados obsoletos y sobrescribir campos de relleno único; necesita corrección antes de integrar.

## What This Changes

El PR separa la creación de tickets eDesk de la escritura de custom fields, añade el catálogo compartido y programa un cron horario para sincronizar datos de pedidos y lotes.

## Best Possible Solution

Mantener el flujo ticket → mensaje → persistencia → datos, pero distinguir rechazos de nombre y valor, preservar campos suprimidos, limpiar valores gestionados obsoletos y cubrir las carreras del refresco con pruebas dirigidas.

Required: false

## Reproduction Assessment

Sí, por código: un rechazo 4018 en un ticket llena la caché global y un siguiente PUT omite ese campo; también se pueden reproducir campos obsoletos con una fuente que deje de emitirlos.

## Solution Assessment

No: desacoplar creación y datos es adecuado, pero la implementación debe recalcular tras el GET fresco, tratar los campos gestionados como un conjunto completo y no compartir rechazos de valor entre tickets.
