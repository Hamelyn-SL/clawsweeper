## Summary

La incidencia sigue siendo necesaria: `dev` ya permite ejecutar clientes provisionales mediante HITL, pero aún escala la columna de cantidad ausente y no crea ni usa un issue de alta como condición de ejecución.

## What This Changes

Eliminar la anomalía por ausencia de columna de cantidad y permitir que el watcher ejecute clientes provisionales tras abrir o reutilizar su issue de alta.

## Best Possible Solution

Separar la normalización de cantidades de la política de ejecución: asumir una unidad por fila sin anomalía y decidir explícitamente si un issue de alta puede sustituir la identidad provisional aprobada en HITL.

## Maintainer Decision

Required: true

Kind: product_direction

Question: ¿Debe un issue de alta abierto permitir al watcher ejecutar con ✅ un cliente provisional, sin que la sesión HITL reciba una identidad explícita?

Rationale: El comportamiento actual se diseñó recientemente para exigir una identidad provisional autorizada y evitar colisiones; el issue propone una política de autorización distinta.

Likely owner: JavierHamelyn

Owner reason: Ha definido y mantenido las protecciones de cliente provisional que esta decisión modificaría.

Owner confidence: high

Options:

- **Mantener HITL explícito (recommended):** Quitar la anomalía de cantidad y crear o enlazar el issue de alta, pero conservar `clientIdentity` autorizada para cada ejecución provisional.
- **Autorizar por issue abierto:** Permitir la ejecución con ✅ cuando el ledger tenga una identidad provisional no reservada y un issue de alta abierto enlazado.
- **Exigir alta permanente:** Conservar el comportamiento actual y usar el issue únicamente para completar `B2B_CLIENTS` antes de cualquier ejecución.

## Reproduction Assessment

Sí, con alta confianza desde código: un fichero sin cantidad añade una anomalía y un cliente no registrado se escala tras el ✅. No se ejecutó una orden real durante esta revisión de solo lectura.

## Solution Assessment

No del todo: eliminar la anomalía de cantidad es un cambio acotado, pero usar un issue abierto como autorización de ejecución requiere validar la política propuesta frente al HITL existente.
